Two improvements based on ideas by [Medium1992](https://github.com/Medium1992) from [mihomo-proxy-ros](https://github.com/Medium1992/mihomo-proxy-ros).

## HTTP/2 flow governor (`h2-flow`)

The client side of an HTTP/2 flow governor for XHTTP in h2 mode. The server sends data only as fast as the client reads it. Without the governor the server fills large HTTP/2 windows (4 MiB per stream in Go) and data nobody reads piles up in memory. The server needs no setup: the governor uses standard HTTP/2 flow control and works with any server.

How it works:

- **Window by consumption.** The governor shows the server a 64 KiB window, caps the frame size at 16 KiB and measures RTT with its own PING once a second. The server gets credit back only while unread data stays below what the client reads in a couple of round trips.
- **Fast start.** A new stream starts with a 256 KiB window or the window the connection recently needed. Until the first RTT is measured, the window opens with every credit.
- **Path model from `min_rtt`.** On Linux and Android the governor reads TCP_INFO from the kernel (`rtt`, `min_rtt`, `rttvar`) and holds a download window to at most `1.25 × highest read rate × min_rtt`. On other systems it uses its PING measurements.
- **Works with a server-side governor.** The same governor exists on the server side in [Jolymmiles/Xray-core](https://github.com/Jolymmiles/Xray-core) (the `h2Flow` option). A governed client announces the default 65535 window, which tells the server that a governor sits on the other side too, so the server does not hold back what it sends. The governor can therefore be on the client, on the server or on both: downloads do not stall and throughput stays the same.

Off by default, enabled per proxy with an `h2-flow` block:

```yaml
xhttp-opts:
  h2-flow:
    enabled: true
    max-stream-receive-window: 16777216      # receive window per stream, bytes
    max-connection-receive-window: 33554432  # receive window per connection, bytes
```

- `enabled` turns the governor on.
- **Receive windows:**
  - optional, from 65535 bytes to 1 GiB;
  - unset, Go's default windows apply (4 MiB per stream);
  - with the governor they are a ceiling and the real window follows reading;
  - without it they are fixed windows.
- `h2-flow-control: true` still works as a shorthand for `h2-flow.enabled: true`. When both are set, `h2-flow.enabled` wins.
- Downloads through `download-settings` use the same `h2-flow` block.

Works only in h2 mode; it has no effect for h3 and http/1.1.

To enable `h2-flow` for Remnawave subscription users, use the Remnawave host mapper; see [XHTTP Flow Control](/for-devs/remnawave-integration/#xhttp-flow-control-h2-flow) on the Remnawave integration page.

## HTTP/2 send buffer: 32 KiB

Long-lived HTTP/2 streams keep their send buffer open for the whole connection: XHTTP in stream-one/stream-up modes and gRPC. Its size is reduced from 512 KiB to **32 KiB** through the [legiz-ru/prizrak-http](https://github.com/legiz-ru/prizrak-http) fork on top of `metacubex/http` v0.1.8. With many concurrent tunnels this saves noticeable memory at the same speed. Nothing to configure.

## GET uploads in packet-up mode

In `packet-up` mode Prizrak-Core can send its upload requests with `GET`, as Xray does with `"uplinkHTTPMethod": "GET"`. The data travels in the request body, in a header or in a cookie, chosen by `uplink-data-placement`. The Prizrak-Core listener accepts such requests from Xray clients as well.

```yaml
xhttp-opts:
  path: /x
  mode: packet-up
  uplink-http-method: GET
  uplink-data-placement: header   # body, header or cookie
```

- `GET` works in `packet-up` mode only. In `stream-one` and `stream-up` the config fails to load with an error.
- The method is case-insensitive: `get` and `GET` are the same.
- `uplink-data-key` defaults as in Xray: `X-Data` for header and `x_data` for cookie. Set it only when the server uses another name.
- For header and cookie one upload is 4 KiB when `sc-max-each-post-bytes` is unset: the Xray server accepts headers up to 8 KiB. The Xray client defaults to 1 MB there and needs that lowered by hand.

Xray option mapping:

| Xray (`xhttpSettings`) | Prizrak-Core (`xhttp-opts`) |
| --- | --- |
| `"mode": "packet-up"` | `mode: packet-up` |
| `"uplinkHTTPMethod": "GET"` | `uplink-http-method: GET` |
| `"uplinkDataPlacement": "header"` | `uplink-data-placement: header` |
| `"uplinkDataKey": "X-Data"` | `uplink-data-key: X-Data` |
| `"scMaxEachPostBytes": "4000"` | `sc-max-each-post-bytes: 4000` |
